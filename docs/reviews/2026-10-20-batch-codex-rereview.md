## 剩余问题：R4 / P2 — 不能把加载后读取的新指纹绑定到旧索引

位置：[scripts/mcp_server.py](../../scripts/mcp_server.py)，第 **130–132** 行；首次加载第 **108–109** 行存在同样问题。

`vector_index.reload(db)` 和后续 `_index_fingerprint(db)` 没有处于同一 SQLite 读快照。若网页导入在前者取完切片之后、后者执行之前提交，新指纹会被保存到旧内存索引上。以后库没有其他变化时，`fingerprint == self._index_fingerprint` 恒真，刷新会一直被跳过。第 131 行注释所说的“下一次调用会再刷新”在这个时序下恰好不会发生；进程内 RLock 也不能阻止另一进程提交。

独立复现（真实 SQLite、真实 reload/search、mock 嵌入，不修改产品代码）：

1. 保持真实 `vector_index.reload`，仅在其返回后、保存指纹前，通过另一个连接提交一个新 ready 文档及有效切片向量，以确定性调度模拟导入竞争。
2. 首次初始化和后续刷新各测一次。
3. 两次均出现：列表含新文档，缓存指纹与数据库指纹完全相等，但连续 **3 次**限定该文档的检索都返回空，`ask_question` 返回 `no_evidence`。
4. 不再改资料，仅重新初始化 KnowledgeBase，两个对照都能召回该文档，定位为索引/指纹版本不一致。

这不是“外部脚本原地改同一 chunk 行”的已声明局限：用例是正常的**新增文档与切片提交**。也不是要求并发提交立即在同一个请求可见；问题是后续请求仍无法自行恢复。本轮常规静态导入后的刷新已经修好，剩余问题只在特定并发时序出现，因此按 P2 反馈。

最小修复方向：

- 让首次加载和后续 reload 所读索引数据、所记录指纹来自**同一数据库读快照**；或采用加载前版本与前后变化检查，确保期间发生的新提交不会被标记为“已加载”。
- 不必重载嵌入模型、增加第二套索引或设计新服务；复用现有加载路径即可。
- 补测首次加载、后续刷新这两个边界；导入期间一次查询可使用一致旧快照，但写入结束后后续查询必须刷新成功。`search_documents` 与 `ask_question` 都要覆盖。
