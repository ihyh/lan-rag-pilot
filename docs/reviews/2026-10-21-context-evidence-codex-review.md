# Codex 复核：续段与字面证据补全

日期：2026-10-21。结论：**要求修改后复审；不建议开启两个候选开关或以准确率提升发布。**

## 审核版本与边界

- 分支 `feat/manual-document-scope-20261020`；初审 `587f9b2`，审核期间新增 `a0a87633e2f4426b562b03dc73799e96aca545ef`，已追加审核。
- 相对功能基线 `f62c23d`，包含续段组装和字面证据补全；本地/远端功能分支均为 `a0a8763`，远端 main 仍为 `abf6d24`。
- `RAG_CONTEXT_CONTINUATION` 与 `RAG_EVIDENCE_COMPLETION` 源码默认均为关闭。这不是对用户当前生产配置的检查或启用确认。
- Codex 仅修改审核报告、忽略的规划/诊断文件；未修改产品、提交、推送、合并、部署、重建生产索引或调用真实 RAG 模型。测试使用隔离库、内存 HTTP 客户端与 mock 生成；读取已有私有答案，但不把原始文档/整套答案放入公开报告。

## 必须处理的发现

### R1 / P1：两个补证入口都会产生无法持久化的来源

位置：`app/context_assembly.py:142`；`app/evidence_completion.py:113`。调用链经过共享 `retrieve_sources`，然后由 `app/routers/query.py` 的 `_store_chat` 保存来源。

新增来源设置 `score=None`，而 `app/db.py:164` 定义 `chat_sources.score REAL NOT NULL`。独立 API 验证分别只开启续段和只开启字面补证：实际检索/组装完成、mock 生成成功后，普通接口返回 HTTP 500，异常为 `NOT NULL constraint failed: chat_sources.score`；流式接口也在保存阶段抛出同一错误，无法正常发送 done。

数据库连接为自动提交，异常前已写入 `status=ok` 的答案和部分来源。续段反例的答案有 3 个来源但只保存 1 个；字面补证反例只保存 2/3，新增引用无法从历史完整恢复。关闭候选开关的普通/流式对照正常。

最小修复要求：让新增来源的“没有检索分数”与持久化契约一致，覆盖旧数据库升级路径，不能伪造相似度绕过检查；确保失败不会留下被标作成功但引用残缺的记录。增加两个开关分别开启的普通/流式/历史来源集成测试。MCP 不经过聊天持久化，不能用其测试通过代替 Web 验收。

### R2 / P2：字面搜索没有标识符边界，且把通配符当成字面

位置：`app/evidence_completion.py:80-81`。

`LIKE '%token%'` 将查询代码 `2,1` 匹配到另一代码 `12,10`，将 `bit4` 匹配到 `bit40`；引号中的 `A_B` 又会匹配 `AXB`，因为 `_` 未转义。三组内存数据库反例都把无关记录作为 `matched_literal` 证据加入，而不是仅返回真正点名的标识符。这会制造伪冲突并占用补证名额。

最小修复要求：SQL 粗召回后做相应类型的完整标识符匹配；转义 LIKE 元字符或采用确实按字面查找的方法。保留准确匹配的正控制，并补代码前后数字、字段后缀、下划线/百分号测试。

### R3 / P2：先截断 40 条，再做文档多样性，仍会漏掉另一份定义

位置：`app/evidence_completion.py:89`，以及 `151-174` 的后续挑选。

构造文档 A 的前 40 个片段均包含代码 `2,1`，文档 B 的第 41 个片段包含同代码的另一解释。实际补证只返回 A 的三个片段，B 从未进入候选；明明仍在“最多 3 段”容量内，却无法实现优先覆盖不同文档。重复片段较多的早期文档会系统性遮住后来导入的文档。

最小修复要求：限制总候选/总输出的同时，在截断之前或分批检索时保证按文档覆盖；不要只把固定 40 改为另一个更大数字。测试早期大文档重复、后续小文档有不同定义，以及已有来源已占部分文档的情况。

### R4 / P2：用工作簿 seq=0 代替目标工作表表头

位置：`app/evidence_completion.py:95-102`、`176-187`。

当前 `_header_row` 无条件选择整份文件的第一个 chunk。反例中工作簿先有 Cover 表，后有 Parameters 表；命中 Parameters 的目标行后，实际附加 Cover 的标题/版本行并标记为 `table_header`，正确的 Parameters 列名没有补入。这会使目标字段、值和单位仍无法按对应列解释。新增来源也在 `query.py` 现有 `table_headers` 赋值循环之后插入，不能依赖那个循环自动补好元数据。

最小修复要求：按目标行所在的工作表/表区域绑定真正表头，复用已有按 sheet 维护的表头信息或可靠原文定位；没有可靠对应时不得标成该行的表头。补多工作表、封面先于数据表、不同表列顺序不同的回归。

### R5 / P2：DOCX 的 seq 邻接不等于原文邻接

位置：`app/context_assembly.py:20`、`123`；关联既有 `app/parsing.py:307-312`。

当前 DOCX 解析先输出全部普通段落，再输出全部表格。独立生成的合成 DOCX 原顺序是“Reader 配置段 → Reader 参数表 → Emergency shutdown 段”，真实 `parse_docx + chunk_units` 输出却是“Reader 段 → Emergency 段 → Reader 表”。本次新增组装把该参数表标作 Emergency 的续段。

解析顺序问题原本已存在，但本次自动利用 seq+1 推断续接关系，新增了确定的错误关联。最小修复可以先排除不能证明原序的 DOCX；若要支持，则需使用保留正文结构顺序的解析与可验证顺序信息。不要以单独修新解析器、忽略旧索引顺序的方式宣称已解决，也不要未经授权重建生产索引。

### R6 / P2：顶层章节标题会被误当成列表续写

位置：`app/context_assembly.py:27`、`34-39`。

前块已完整结束于 `Byte 1: Timeout ... (default 40).`，下一页开头为 `6. Emergency shutdown`。`NEW_SECTION` 只识别 `6.1` 一类多级数字标题，`CONTINUATION_START` 却将 `6.` 当作编号续写，最终把无关新章作为前块续段加入。换成 `6.1 Emergency shutdown` 的正控制不会附加，证明是边界识别缺口。

最小修复要求：不能仅凭“数字加点”或缺少句号认定续接；结合可靠章节/列表结构，无法确认时不要标为续文。测试顶层章节、Markdown 标题、独立参数标题与真正连续编号列表，避免只针对一个反例补正则。

### R7 / P2：块内稍后出现新章节，会把前面的真正续文一起丢掉

位置：`app/context_assembly.py:81-85`、`129-130`。

下一块依次为 `Byte 2 ...`、`Byte 3 ...`、`5.4 Reset command`。真实 chunk_units 保留同页这些行，但 `_looks_like_new_section` 扫描前 5 行，发现第三行标题后否决整块，Byte2/3 仍然漏掉。删除后面的新章标题便能补入，是明确反例与正控制，不是缺少原文。

最小修复要求：区分“开头即新章节”和“续文后才开始新章节”；保留新章节前的必要原文，并维持可追溯的来源位置/区间，不能为避免噪声而连真正续文一起丢弃。

## 准确率声明需要更正

- `docs/CONTEXT_CONTINUATION.md:48-49` 的 H05 必要来源覆盖从 1/2 到 2/2 可以由已保存结果核实，但“单位均完整”的成功描述不成立。两个候选保存答案都把所有参数单位概括成时间单位，而其中一个字段实际是重试计数。不能把“证据齐了”记成“答案正确了”。
- 固定选择原基线与最终续段候选，核对 12 题：1 题来源交集增加、0 题下降；25 条使用样本：交集 0 增加、0 下降。这里的使用样本参考是历史检索来源，不是人工确认的全部必要证据；该统计不等于答案正确率或无新增误答。
- 私有 `compare_continuation.py` 按修改时间自动挑最新两份；随着两次续段修订、又加入字面补证，新旧文件并不稳定代表 OFF/ON。结果行没有保存 Git SHA/候选开关等运行配置，因此需显式固定比较文件和配置，不根据“最新”推断实验条件。
- `run_diagnosis.py` 直接调用 `retrieve_sources + llm.chat`，没有经过 HTTP 聊天持久化，所以保存答案不能排除 R1。最新 `EVIDENCE_COMPLETION.md` 已明确承认证据覆盖改善不代表准确率提升，应保留这个区分。
- 下一轮不需要新评测平台：补运行身份、按“字段值/单位/条件/来源是否支持”逐项核对，并保留初次答案和失败记录。没有用户确认的业务验收集，不能报告普遍业务准确率提升。
