## R1 · P2：首问生成期间仍能改动文档，显示范围与实际请求不一致

位置：[app.js:419](../../app/static/js/app.js#L419)–434，及同文件 `toggleDocument`、chip 删除事件。

复现：选 Alpha（ID=1）发送首问，保持请求未完成，此时 `S.busy=true`、`S.currentId=null`。新的复选框和“仅选”按钮 `disabled=false`，点击 Beta（ID=2）的“仅选”，界面已选名称变为 Beta，实际在途请求仍是 `document_ids:[1]`。chip 删除同样没有 busy 防护。请求成功后会恢复为服务器范围，但等待期间的显示已经不真实。

这是相对旧版的交互退化：旧 `updateScopeControls` 会按 busy 禁用复选框，新渲染只禁用了单选模式和部分工具栏按钮。

最小修复：busy 时禁用所有修改范围的入口，并在共用选择修改函数/“仅选”处理器增加 busy/locked 防护，避免旧节点的事件或程序调用绕过；不需要新状态机。可以在首问发出后显示“本次范围已固定，正在生成”。

复测：用可控延迟的请求测试 checkbox、仅选、chip 删除、设备/全选/清空；请求完成前范围不变。模拟失败/停止后，可再次编辑正确的草稿；成功后沿用服务器的固定范围。

## R2 · P2：历史恢复忽略服务端 scope_mode，限定会话被误标全库

位置：[app.js:330](../../app/static/js/app.js#L330)–334；调用方 `renderConversation` 只传 `document_ids`，不传返回的模式。

后端已专门保留真实模式：当原选定文档不再对账号可见，真实详情会返回 `scope_mode:"selected", document_ids:[]`。独立 API 实测得到该组合；前端据 `ids.length` 推断为 `all`，实际徽标显示“全库检索（已固定）”。

影响是范围显示错误，不是已证实的全库检索绕过；服务器仍保存原范围，不能把此问题描述成数据泄漏。即便个人管理员不常触发这一场景，也应完成新增 API 字段与前端的正确对接。

最小修复：恢复详情时优先使用并校验服务端 `scope_mode`；仅为没有此字段的旧响应保留 ID 推断。`selected + []` 显示“原限定文档当前不可用”，引导新建会话，不伪装为全库，也不暴露已隐藏 ID。无需数据库迁移。

复测：覆盖 `selected + 非空ID`、`all + []`、`selected + []` 及不含模式的旧响应；刷新、点击历史、首问结束后的详情恢复均一致。现有沙箱历史用例没有传 `scope_mode`，因此漏掉了该缺陷。

## R3 · P2：全选不遵守现有 100 文档上限，界面允许必失败的请求

位置：[app.js:940](../../app/static/js/app.js#L940)–942，及 `scopeBlockReason`；后端限制在 [schemas.py:38](../../app/schemas.py#L38)。

复现：列表提供 101 份就绪文档 → 点击全选 → `newDocumentIds.length=101`，发送前 `scopeBlockReason()` 返回空字符串。相同列表的真实 HTTP 请求被 Pydantic 的 `max_length=100` 拒绝（422）。用户此前的输入已经按发送流程清空。

最小修复：保留现有后端上限，在前端选择/全选与发送前明确校验并展示上限。不要静默截取前 100 份，更不要自动切为全库；否则实际范围与用户选择不一致。若要改变后端上限，另说明依据和代价，不能只删校验。

复测：100 项可以发送；101 项不能发出请求且保留输入/选择，提示用户减少范围。全选、筛选后累加、逐一勾选和设备快捷入口均覆盖。
