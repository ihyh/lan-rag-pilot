## 本轮发现

### R8 / P2：精确过滤之前截断每个文档，仍会漏掉存在的准确标识符

位置：`app/evidence_completion.py:133-141`，尤其 `LIMIT MAX_ROWS_PER_DOCUMENT` 在 `matcher.search` 之前。

修复按文档分别召回解决了原“文档 A 前 40 条挤掉文档 B”的反例，但每份文档只读取前 4 条 SQL 子串匹配，之后才进行精确匹配。一个文档依次有四条 `bit40 = other`、第五条 `bit4 = target` 时，查询 `bit4是什么` 得到空补证列表。移除一条 bit40、让真正 bit4 位于第四条，即能正常返回。伪匹配虽然不再进入上下文，却仍占用了候选窗口，造成真实目标被静默漏掉。

修复要求：在精确匹配后的有效候选上应用名额，或有界分批继续读取到找到足够准确匹配/穷尽文档；不要仅增大固定 4。加入“前四条全部过滤、第五条真匹配”、代码对/短字段的同类反例，继续验证跨文档优先级和数量上限。

### R9 / P2：同一工作表的首行仍被无条件当作真正表头

位置：`app/evidence_completion.py:175-189`。

原来跨工作表取错 Cover 表的问题已修复，但 `_header_chunks` 只检查目标 sheet 的“第 1 行”文本存在，没有确认该行是列名。反例：Parameters 第 1 行是单格标题，第 2 行才是 `Name / Unit`，第 3 行是目标参数。实际补入第 3 行和第 1 行，标题被标为 `table_header`，真正列名仍缺失。已有 `app/index.py` 表头识别至少检查明确字段角色；新补证不能仅凭行号绕过“可靠表头”的判定。

修复要求：确认对应列名/区域，或复用已有可靠表头元数据；暂不支持第二行表头也应如实保留未知，而不是把标题标成表头。加入同表标题先于列名、空白首行、列名不在第 1 行的测试。该反例最低要求是不得将标题作为表头；支持识别第二行是后续能力选择，不要求为了本次修复重建生产索引。

### R10 / P2：小数参数行被误判为章节，裁掉必要值和后续定义

位置：`app/context_assembly.py:42`、`89-94`。

新的 `NEW_SECTION` 数字标题规则可以把 `0.5 seconds.` 匹配成“0.”标题。下一片段为：

```text
Byte 2: Wait time.
The value below is the maximum.
0.5 seconds.
Byte 3: Retry count is 2.
```

实际送入候选来源的内容只保留前两行，`trimmed_at_section=True`，关键值 0.5 和 Byte3 均消失。原“真正续文之后才出现 5.4 新章”的反例已通过，但现在会把正常数值误当作裁剪点，再次制造残缺证据。

修复要求：区分数字参数/小数值与章节标记，不能只看到数字加点就裁剪；补整数/小数/带单位值及确实新章节的正反控制。无法证明是新章节时，不应据此删除已经确认属于续文的数值。
