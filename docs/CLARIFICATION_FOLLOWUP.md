用户可在自己的成功回复下点击“补充这题”，再补充设备、协议或版本。检索与回答会收到原问题及这条关联链上的全部用户补充；原始输入分别保留，历史可展开核对完整关联问题。普通提问不会自动绑定，也不从助手措辞猜测用户意图。

## 交互与接口

- 输入区显示当前关联目标，可取消；取消保留草稿。首次选择或取消后重新选择可使用已有草稿；已有目标且有草稿时，改绑另一题会提示，不能悄悄改绑。
- 成功后清除当前关联；请求失败保留关联并在输入框为空时恢复草稿。新建、切换、删除、刷新及后退缓存恢复不延续当前选择。发送中或中文输入法组合中不能切换目标。
- `POST /api/query` 新增可选正整数 `followup_to`，同时必须传入 `conversation_id`。必须关联同用户、同会话、当前可见且成功的记录。范围仍由首问固定，不因补充扩大；失败轮不能作为目标，无命中提示的成功记录可继续补充。
- 服务端以真实原始用户输入重建关联，不能用助手答案或旧话题作为检索内容。共享语义/关键词检索、选段、确定性回答及同步/流式生成接收同一 `effective_question`。显式关联时不附带普通历史。
- 最多关联4条既有用户输入（最终最多原问加4次补充）；含标签的完整有效问题不超过2000字符。超限明确拒绝，不截断。删除、损坏、跨会话、跨用户或撤权不能静默退成新问题。

## 保存与兼容

`chats.followup_context` 是新增的可空 TEXT 列，旧记录保持 NULL，不回填原问。仅关联记录保存 `format / parent_chat_id / chat_ids / effective_question` 快照；`question` 仍保存该次原始输入。会话与单条历史只返回校验后的 `followup` 对象或 NULL，不直接暴露内部 JSON 列。

普通历史仍有3轮/2000字符预算，本轮改为先留完整用户问题，再分配助手答案预算，避免长答挤掉原问。这不代表普通提问会自动回溯整条关联，也不证明所有自然语言追问都能理解。
